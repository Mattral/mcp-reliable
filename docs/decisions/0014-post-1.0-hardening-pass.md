# 0014 — Post-1.0 hardening pass: stale tag, dependency audit, small polish

## Status

Accepted. The tag-pointer bug is confirmed but **not yet fixed on the
real remote** — see "The stale tag: what was believed vs. what turned out
true" below for why this ADR documents the bug and the fix commands but
can't itself close the loop.

## Context

The project's working notes listed a short list of low-risk, well-specified
follow-up items after the v1.0.0 publish: verify the git tag, refresh `README.md`
with real npm links, and a handful of small CLI/docs polish items. This
ADR records what was found and decided while working through that list,
following the same "own mistakes in writing" practice as every other ADR
that documents a bug (see ADR 0005, ADR 0009, ADR 0010, ADR 0011).

## The stale tag: what was believed vs. what turned out true

**Believed:** the `v1.0.0` git tag might be stale, per the working notes'
own caution — `git tag -a v1.0.0` had failed with "tag already exists"
during the original release, which the notes flagged as a signal worth
checking rather than something already confirmed broken.

**What turned out true, verified by actually cloning the real remote**
(`git clone https://github.com/Mattral/mcp-reliable.git`, not reasoned
about from the local working copy alone): the tag is genuinely stale.

```
git log v1.0.0 --oneline -1   →  9285d7b docs: add PUBLISHING.md and v1.0.0 release notes...
git log HEAD --oneline -1     →  ddd208b docs: note the npm scope rename in the 1.0.0 changelog entry
```

`HEAD` is six commits ahead of the tag, and those six commits are exactly
the `@mcp-reliable` → `@mattral` scope rename (ADR 0013) plus its own
changelog note. Confirmed concretely — not just by commit message, but by
diffing the actual file content:

```
git show v1.0.0:packages/core/package.json | grep name
  → "name": "@mcp-reliable/core"
git show HEAD:packages/core/package.json | grep name
  → "name": "@mattral/core"
```

Anyone running `git checkout v1.0.0` today gets source that imports and
declares the unavailable, never-published `@mcp-reliable/*` scope — which
doesn't match what's actually installable from npm (`@mattral/*`). The
tag and the published packages disagree with each other.

**Why this ADR doesn't close the loop:** fixing this requires `git push
--force` (or deleting and recreating the tag) against
`github.com/Mattral/mcp-reliable` with write credentials this assistant
doesn't have — cloning is possible over HTTPS without authentication, but
pushing isn't. The exact fix commands are recorded in
[`PUBLISHING.md`](../../PUBLISHING.md#5-tag-and-push) (step 5) for the
maintainer to run directly:

```
git tag -d v1.0.0
git tag -a v1.0.0 -m "v1.0.0" HEAD
git push origin v1.0.0 --force
```

## Dependency audit: re-verified, not just re-trusted

`npm audit` on a fresh `npm install` reported four advisories, not the
one (`esbuild`) `testing.md` documented at the time of the v1.0.0
release. Advisories change over time as new ones get published — this
isn't a regression, just a signal that hadn't been checked since. Each of
the three new findings was traced to its actual reachability rather than
accepted or dismissed by category:

- `@hono/node-server` (Windows path traversal, `<2.0.5`) — `npm ls
  @hono/node-server` shows the vulnerable `1.19.15` copy exists only
  nested under `@modelcontextprotocol/sdk`'s own optional HTTP-transport
  helper. `@mattral/agent-interface` never imports anything but
  `StdioServerTransport` (confirmed by grepping its own source, not
  assumed), so that code path is dead in this project's actual runtime.
  `@mattral/server`'s own direct dependency already resolves to the
  patched `2.0.11`.
- `brace-expansion` (DoS) — reachable only through `eslint` and
  `@vitest/coverage-v8`'s own transitive `minimatch`/`glob` dependencies.
  Dev tooling only.
- `react-router` (`GHSA-qwww-vcr4-c8h2`, RSC-mode CSRF bypass) — the
  advisory itself scopes the exploit to react-router's *unstable RSC
  APIs*. `@mattral/dashboard` is a plain client-rendered Vite SPA with
  ordinary hash-based routing (ADR 0008) — no RSC, no server actions, no
  code path the advisory describes.

**Decision:** don't force a react-router v8 major-version bump (the only
available "fix" for that advisory) to resolve a finding that isn't
actually reachable in how this dashboard is built — the breaking-change
risk isn't justified by a real reduction in exposure. Documented in full
in [`docs/testing.md#dependency-audit-status`](../testing.md#dependency-audit-status)
instead, matching how the pre-existing `esbuild` finding was already
handled. Revisit if a *v8* migration becomes worthwhile for its own
features, or if this specific advisory's scope is later found to be
broader than currently documented.

## Small polish items completed in this pass

- `packages/server/package.json` gained a `start` script (`node
  dist/index.js`) — previously only runnable via that exact `node`
  invocation, not discoverable via `npm run`.
- `monitor`'s health-check connection timeout (`HealthChecker`'s existing
  `timeoutMs` option, default 10s) is now exposed as `mcp-reliable
  monitor --timeout <ms>` — previously hard-coded regardless of CLI
  input. Adding this as a third flag needing the same
  parse-a-positive-integer-or-error validation `--interval` and
  `--window` already had inline was the actual "rule of three" trigger
  ADR 0006 defines — extracted into an exported, independently-tested
  `parsePositiveMs` helper in `packages/cli/src/commands/monitor.ts`
  rather than duplicated a third time.
- `PUBLISHING.md`'s post-publish smoke-test example used a Unix-only
  `/tmp/...` path that fails under Windows `cmd.exe`. Replaced with
  parallel macOS/Linux, PowerShell, and `cmd.exe` versions, since this
  project is actually published from Windows day to day.
- `PUBLISHING.md` now documents the npm CLI's own known bug
  ([npm/cli#7302](https://github.com/npm/cli/issues/7302)) — a
  scary-looking but harmless `bin[...] was invalid and removed` warning
  seen during the real v1.0.0 publish — so it doesn't cause alarm on the
  next release.

## Consequences

- `README.md` gained real links to the live npm packages and the same
  "verified live, not just locally" framing `RELEASE_NOTES_v1.0.0.md`
  already had — see the README diff in this same body of work.
- The maintainer still has one manual step outside this assistant's
  reach: running the tag fix commands above against the real GitHub
  remote. Everything else in this pass is complete and verified (full
  `npm run lint && npm run build && npm test` re-run clean afterward).
